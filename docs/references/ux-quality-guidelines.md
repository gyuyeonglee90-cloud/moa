# 앱 품질 및 UX 지침 (대표 제공 원문)

앱을 설계하거나 구현할 때 기능 요구사항뿐 아니라 사용성, 접근성, 이해하기 쉬운 콘텐츠, 오류 예방을 함께 고려한다. 완성 후에는 아래 기준으로 자체 점검하고, 미충족 항목과 적용할 수 없는 항목을 이유와 함께 기록한다.

## 1. 기준 적용 원칙

- 사용성은 ISO 9241-11의 관점에 따라 평가한다.
  - 사용자가 의도한 목표를 **효과적으로** 달성할 수 있는가?
  - 필요한 시간과 노력 면에서 **효율적인가?**
  - 사용자가 **만족스럽고 편안하게** 사용할 수 있는가?
- 접근성은 가능한 한 **WCAG 2.2 AA**를 기준으로 고려한다.
- 모바일 UI는 해당 플랫폼의 공식 가이드를 따른다.
  - iOS: Apple Human Interface Guidelines
  - Android: Android Accessibility 및 Material Design 가이드
- 기준을 기계적으로 적용하지 말고 앱의 주요 사용자, 과업, 기기, 사용 환경을 고려한다. 기준에서 벗어나는 경우에는 이유와 사용자 영향을 설명한다.

## 2. 사용자가 목표를 쉽게 달성하는가

- 앱의 핵심 사용자가 누구인지, 가장 중요한 과업이 무엇인지 먼저 파악한다.
- 핵심 과업은 불필요한 단계나 반복 입력 없이 완료할 수 있게 설계한다.
- 사용자가 현재 위치, 가능한 다음 행동, 작업 완료 여부를 알 수 있게 한다.
- 중요한 기능은 쉽게 찾고 실행할 수 있도록 배치한다.
- 입력값을 유지하거나 되돌리기·취소하기·다시 시도하기가 필요한 상황을 고려한다.
- 성공률, 완료 시간, 오류·되돌아가기 횟수 등으로 핵심 과업의 사용성을 확인할 수 있게 설계한다.

## 3. 화면과 조작 요소

- 버튼과 링크에는 실제로 실행될 행동을 분명하게 표현한다.
  - 예: `확인`보다 `예약 확정`
- 서로 다른 행동이 헷갈리거나 실수로 눌리지 않도록 시각적으로 구분한다.
- 터치 UI의 조작 영역은 플랫폼 가이드를 따른다.
  - iOS: 일반적으로 최소 44×44pt 권장
  - Android: 일반적으로 최소 48×48dp 권장
  - 웹: WCAG 2.2의 타깃 크기 기준과 예외 조건 확인
- 아이콘만으로 기능을 표현할 때는 의미가 명확한지 확인하고, 필요한 경우 접근 가능한 이름을 제공한다.
- 화면 확대, 긴 텍스트, 다양한 화면 크기에서도 콘텐츠와 조작 요소가 가려지거나 잘리지 않는지 확인한다.
- 화면마다 같은 기능은 같은 이름, 위치, 동작 방식을 유지한다.

## 4. 문구와 언어

- 쉬운 일상 언어를 우선 사용하고, 전문용어·약어는 꼭 필요할 때 설명한다.
- 짧고 구체적인 문장으로 안내한다. 모호한 표현이나 내부 용어는 피한다.
- 버튼, 메뉴, 오류 메시지는 사용자가 무엇을 할 수 있고 어떤 결과가 생기는지 알려준다.
- 숫자·날짜·단위·통화·시간대는 사용자와 사용 지역에 맞게 표시한다.
- 여러 언어를 지원한다면 번역 길이 차이, 날짜·숫자 형식, 글자 잘림을 고려한다.

## 5. 접근성과 정보 전달

- 텍스트와 배경의 색상 대비가 충분한지 확인한다.
- 색상만으로 상태나 오류를 구분하지 않는다. 텍스트·아이콘 등 다른 단서도 함께 제공한다.
- 키보드로 모든 핵심 기능을 사용할 수 있게 하고, 현재 포커스 위치가 보이게 한다.
- 스크린 리더가 제목, 입력 요소, 버튼의 이름과 상태를 이해할 수 있도록 한다.
- 이미지가 정보를 전달한다면 대체 텍스트를 제공한다. 장식용 이미지는 보조기기에서 불필요하게 읽히지 않도록 한다.
- 글자 크기를 키우거나 화면을 확대해도 콘텐츠가 겹치거나 기능을 잃지 않는지 확인한다.
- 입력 오류는 문제가 있는 위치와 수정 방법을 구체적으로 안내한다.

## 6. 오류 예방과 신뢰

- 입력 형식, 필수 조건, 제한 사항을 입력 전에 알려 실수를 예방한다.
- 오류 메시지는 원인과 해결 방법을 함께 설명한다.
- 저장·삭제·결제처럼 영향이 큰 행동은 결과를 미리 알리고, 필요한 경우 되돌릴 방법을 제공한다.
- 로딩, 빈 화면, 네트워크 오류, 권한 거부, 데이터 없음 상태를 설계한다.
- 권한을 요청할 때는 필요한 이유와 기능상 영향을 설명한다.
- 사용자에게 보이지 않는 실패나 조용히 무시되는 입력이 없는지 확인한다.

## 7. 구현 후 자체 점검

작업 완료 시 다음 내용을 간단히 보고한다.

1. 핵심 사용자와 주요 과업
2. 사용성·접근성·플랫폼 가이드에서 적용한 기준
3. 핵심 과업을 실제로 따라가며 발견한 막힘이나 모호한 점
4. 기준을 충족하지 못했거나 적용하지 않은 항목과 그 이유
5. 남은 품질 위험과 추가 검증이 필요한 부분

가능하면 대표적인 사용자 과업을 기준으로 화면을 직접 점검한다. 자동화 도구 결과만으로 접근성이나 사용성이 충분하다고 단정하지 않는다.
